# Playtesting

Playtests validate social/ecological behavior, not feature count.

## Kill / validation gates

### After M1 — multiplayer foundation
If joining, authority, shared-object interaction or multi-instance iteration is unstable or unpleasant, solve it before adding creature systems.

### After M3 — Broodhorn problem
The four-player Broodhorn/Hushmallow scenario should naturally produce negotiation, laughter, frustration and adaptation. If it does not, stop adding species and revisit the core social/ecology loop.

Questions:
- Did players negotiate creature placement?
- Did they understand why Hushmallows failed to sleep/productively function?
- Did Broodhorn noise create funny frustration rather than opaque annoyance?
- Did players adapt their layout/behavior?
- Was feedback readable without exposing raw simulation numbers?
- Did players discover an obvious dominant layout/strategy?

### After M5 — rocket economy
If five-minute cycles do not generate urgency, scarcity and meaningful opportunity cost, stop progression work and fix the economy.

### After M8 — complete ugly match
If a 30–60 minute match from lobby to extraction is not fun, do not begin serious production art.

### After M9 — personal objectives
If private goals mostly create irritation/grief rather than funny selfishness, redesign them before considering saboteur mode.

## Logging
For early tests use structured notes plus lightweight event logging only. Record session seed, player count, duration, major phase timing, creature placements/interactions, objective outcomes and notable failure/confusion moments. Do not build a production analytics platform yet.
